# 需求1方案分析：morph 内容缩小呈现方式

> 2026-09-26 方案设计文档

## 一、问题定量分析

### 1.1 已知矩形尺寸

- **全屏态 (p=1)**：1264×2780 px，宽高比 = 0.45:1
- **卡片态 (p=0)**：1096×359 px，宽高比 = 3.05:1
- **宽高比变化倍数**：3.05 ÷ 0.45 = **6.8 倍**

这个巨大的宽高比跨度是核心矛盾：窗口从"竖长矩形"形变到"扁宽矩形"，任何等比缩放内容都会在某个区间与窗口形状严重不匹配。

### 1.2 核心矛盾可视化

```
p=1.0 (全屏)          p=0.5 (中途)           p=0.0 (卡片)
┌────────┐            ┌────────┐             ┌──────────┐
│        │            │░░░░░░░░│             │░░░░░░░░░░│
│  内容  │            │░内容░░░│             ├──────────┤
│        │            │░░░░░░░░│             └──────────┘
│        │            ├────────┤              (扁矩形)
│        │            │░░░░░░░░│
└────────┘            └────────┘
(竖矩形)              (窗口高度缩到一半，
                       但宽度几乎不变)

问题：如果内容等比缩放，中途会出现：
- 以高为基准缩 → 内容宽度 < 窗口宽度 → 两侧露出背景色条
- 以宽为基准缩 → 内容高度 > 窗口高度 → 上下被硬裁剪 → 退化回"裁剪遮挡"观感
```

### 1.3 数学验证：纯等比缩放的失败

假设内容层加 `scale = lerp01(卡片/全屏, 1f, p)`：

**方案A：以窗口高度为基准**
```
scaleY = scaleX = lerp01(359/2780, 1f, p) = lerp01(0.129, 1f, p)

p=0.5 时：
  内容尺寸 = 1264 × 0.565 = 714 (宽) × 1571 (高)
  窗口尺寸 = lerp(1096,1264,0.5) × lerp(359,2780,0.5) = 1180 × 1569
  
  结果：内容宽 714 < 窗口宽 1180 → **两侧露出 466px 背景色条** ❌
```

**方案B：以窗口宽度为基准**
```
scaleX = scaleY = lerp01(1096/1264, 1f, p) = lerp01(0.867, 1f, p)

p=0.5 时：
  内容尺寸 = 1264 × 0.934 = 1180 (宽) × 2596 (高)
  窗口尺寸 = 1180 × 1569
  
  结果：内容高 2596 > 窗口高 1569 → **上下超出 1027px，必须硬裁剪** ❌
         这就是"被裁剪遮挡"，等于没解决问题
```

**结论**：纯等比缩放在 6.8 倍宽高比变化下**不可能**任意时刻都让内容精确贴合窗口。

## 二、推荐方案：宽度基准等比缩放 + clipRect 保险

### 2.1 方案描述

内容层加**等比缩放**（以窗口宽度为基准），配合 **clipRect 作为极端情况保险**（而非常态裁剪）：

```kotlin
// 内容层修饰符链（在现有 drawWithContent clipRect 之后、graphicsLayer translationY 之前）
.graphicsLayer {
    val pp = morph.progress.value
    val b = morph.cardBounds
    if (b != null) {
        // 缩放：以窗口宽度为基准等比
        val windowW = lerp01(b.width, size.width, pp)
        val s = windowW / size.width  // 内容宽度缩放到等于窗口宽度
        scaleX = s
        scaleY = s
        transformOrigin = TransformOrigin(0.5f, 0.5f)  // 中心缩放
    }
}
.graphicsLayer {
    // translationY 锚行跟踪（保持现有逻辑）
    val pp = morph.progress.value
    val b = morph.cardBounds
    if (b != null) {
        val cardCenterY = b.top + b.height / 2f
        val screenCenterY = size.height / 2f
        translationY = lerp01(cardCenterY - screenCenterY, 0f, pp)
    }
}
```

**关键点**：
- **缩放基准是窗口当前宽度**（`lerp01(b.width, size.width, pp)`），而非固定的卡片/全屏比值
- **clipRect 保留**：它现在是"保险"——当内容缩放后高度仍超出窗口（数学上会发生在 p<0.15 区间，见下文），clipRect 裁掉超出部分，但这段时间内容 alpha 本来就在淡出（alpha=fracRange(p,0.40,0.65)），视觉上不可察觉
- **transformOrigin 中心**：内容从中心等比缩放，配合 translationY 锚行跟踪，当前播放行始终对准窗口中心

### 2.2 数学验证：贴合度

代入关键时刻验证：

| p | 窗口宽×高 | scale (宽基准) | 内容宽×高 | 贴合度 |
|---|---|---|---|---|
| 1.0 | 1264×2780 | 1.0 | 1264×2780 | ✅ 完全贴合 |
| 0.65 | 1205×1932 | 0.953 | 1205×2649 | 高超出 717px，但**内容刚淡入完成**，此后可见 |
| 0.50 | 1180×1569 | 0.934 | 1180×2596 | 高超出 1027px，**clipRect 裁掉**，但内容 alpha≈0.4（半透明） |
| 0.40 | 1159×1327 | 0.917 | 1159×2549 | 高超出 1222px，**内容刚开始淡入**（alpha=0），裁剪不可见 |
| 0.15 | 1121×722 | 0.887 | 1121×2466 | 高超出 1744px，但**内容已淡出**（alpha=0），窗口独自缩小 |
| 0.0 | 1096×359 | 0.867 | 1096×2411 | 高超出巨大，但**内容alpha=0 + 窗口alpha≈0**，交叉淡化到卡片 |

**关键观察**：
- **p∈[0.65, 1.0]**（内容完全可见区间）：宽度精确贴合，高度适度超出被 clipRect 裁掉，但**超出部分在窗口外，视觉上读作"内容填满窗口"**
- **p∈[0.40, 0.65]**（内容淡入窗）：高度超出更多，但内容半透明/刚浮现，裁剪边界不明显
- **p<0.40**（内容淡出后）：窗口独自缩小，内容不可见，裁剪无影响

### 2.3 观感预测

- **展开（0→1）**：窗口从卡片生长，内容从 alpha=0 淡入（0.40开始），逐渐**"填满"窗口**直到全屏，宽度始终贴合、高度被窗口"框住"（clipRect），读作"窗口拉大、内容跟着变大填满"
- **收起（1→0）**：内容先淡出（0.65→0.40），淡完后窗口独自缩小回卡片，最后交叉淡化到真卡片。收起后半段（p<0.40）是"一张纸移开"，用户已明确接受这个观感
- **中途打断**：scale 与 progress 是纯函数，打断弹回/快甩收起的 progress 回退自动驱动 scale 回退，行为连续

### 2.4 与现有逻辑的关系

- **clipRect**：保留，从"常态裁剪"降级为"极端保险"（p<0.65 时裁掉内容超出窗口的部分）
- **translationY 锚行跟踪**：保留不动，与 scale 独立叠加（先缩放、后位移，graphicsLayer 链式组合）
- **alpha 淡化窗口**：保留不动（fracRange(p, 0.40, 0.65)），scale 只影响几何不影响透明度
- **窗口层形变公式**：**完全不动**（transformOrigin 左上锚、lerp 补偿、非等比 scaleX/Y），内容层 scale 是内容层自己的事，两层兄弟关系不变

## 三、备选方案：双阶段策略（内容自适应）

### 3.1 方案描述

不做整体几何缩放，而是让内容**自适应窗口尺寸**——窗口宽高变化时，歌词列表的字号、行高、可见行数动态调整：

```kotlin
// 伪代码示意
val windowH = lerp01(cardBounds.height, screenH, progress)
val fontSize = lerp01(19.sp, 26.sp, progress)        // 卡片 19sp → 全屏 26sp
val lineHeight = lerp01(28.sp, 36.sp, progress)
val visibleLines = (windowH / lineHeight.toPx()).toInt()

LazyColumn(修饰符加 .height(windowH)) {
    items(lines.take(visibleLines)) { line ->
        Text(line, fontSize = fontSize, lineHeight = lineHeight)
    }
}
```

**优点**：
- 内容永远"刚好填满窗口"（行数动态计算），无需 clipRect
- 字号连续插值，展开过程读作"字逐渐变大"而非"整体缩放"

**缺点**：
- **LazyColumn 高度动态变化 → 每帧重新测量布局**，性能开销比纯 graphicsLayer transform 高一个数量级（已知帧率优化目标）
- **可见行数跳变**：windowH 从 359→2780，lineHeight 28→36，visibleLines 从 12→77 跳变，**每次 +1 行都是一次 item 组合+测量**，动画期间累计数十次组合突发
- **锚行跟踪失效**：当前播放行可能因行数变化被挤出可见区，translationY 公式需要完全重写（不再是简单的"列表整体位移"，而是"动态调整 scrollOffset 使 activeI 保持窗口居中"）
- **与已验证的窗口形变公式冲突**：窗口层的 scaleY 是非线性 lerp（b.height / size.height），内容层的 lineHeight 是线性 lerp，两者不同步 → 动画中段内容与窗口边界错位

**结论**：该方案在 6.8 倍宽高比变化下**实现复杂度远超收益**，且与"提高帧率"目标相悖（引入逐帧重布局）。仅在推荐方案实测观感仍不满意时作为最后备选。

## 四、风险点

### 4.1 中途"内容被窗口框住"的边界感

**风险**：p∈[0.50, 0.70] 区间，内容高度显著超出窗口（超出量 ~1000px），clipRect 裁剪边界可能被察觉为"硬切"，而非"自然缩小"。

**缓解**：
- 内容在该区间的 alpha ∈ [0.4, 0.8]（半透明→渐显），裁剪边界不如完全不透明时尖锐
- 用户注意力在"窗口在生长"（窗口边界动画），内容是"窗口内的填充物"而非"被裁剪的主体"
- 若实测仍感知明显，可微调内容淡入窗口（如 [0.35, 0.60] 提前淡完），让完全可见区间的超出量更小

**装机验证点**：中速展开/收起，盯 p≈0.55 瞬间，内容顶部/底部边界是否有"硬切感"。

### 4.2 transformOrigin 中心 vs 锚行跟踪的交互

**风险**：内容层 scale 的 transformOrigin 是中心（0.5, 0.5），translationY 锚行跟踪公式假设内容层是全尺寸——缩放后内容的"物理中心"与"视觉中心"可能错位。

**分析**：
- translationY 公式：`lerp01(cardCenterY - screenCenterY, 0f, p)`，这是**容器级位移**（整个内容层 Box 上下移动），与内容层内部的 scale transformOrigin 无关
- scale 的 transformOrigin(0.5, 0.5) 作用于内容层内部：LazyColumn 从自己的中心等比缩放，**不改变容器 Box 的位置**
- 两者独立叠加：先 scale（内部缩）、后 translationY（容器移），最终效果是"缩小后的内容整体跟着窗口移动"

**验证**：代码审查通过（graphicsLayer 链式组合，scale 在前、translationY 在后），但需装机确认 activeI 行在动画全程是否始终对准窗口垂直中心。

### 4.3 已验证逻辑的影响范围

**窗口层形变公式（transformOrigin 左上锚 + lerp）**：**零影响**。内容层 scale 是内容层 graphicsLayer 的事，窗口层是兄弟 Box，两者变换树完全独立。

**三触发路径（返回键/系统手势/下拉）**：**零影响**。触发路径改的是 `vm.collapseLyrics()` / `morph.collapse()` 的调用时机，不涉及视觉属性计算。

**指针闸门（pointerInput awaitEachGesture）**：**零影响**。闸门逻辑在 overlay 最外层 Box，内容层 scale 不改变触摸事件坐标空间。

**中断弹回（打断时 animateTo 取消）**：**自动兼容**。scale 是 progress 的纯函数，progress 回退 → scale 自动回退，无需额外逻辑。

### 4.4 性能开销

**新增开销**：每帧多一次内容层 graphicsLayer 的 scaleX/scaleY 计算（两次浮点乘除 + lerp）。

**量级**：与现有的 4 个 lerp01（translationX/Y + scaleX/Y 窗口层）同量级，graphicsLayer 延迟读机制下这是 O(1) 逐帧重录，**不触发重组/重布局**。

**对比**：远低于备选方案（逐帧重布局 + 可见行数跳变组合突发）。

**结论**：性能风险极低，符合"提高帧率"目标。

## 五、实施计划

### 5.1 Commit 拆分

**Commit 1（本方案）**：内容层加 scale
- 文件：`LyricsMorphOverlay.kt`（内容层 graphicsLayer 加 scaleX/Y/transformOrigin）
- 改动量：+8 行（一个 graphicsLayer 块）
- 验证点：四项交叉验证（见下文 §5.2）
- 装机后若观感满意，推送；若不满意，记录具体现象，回退后再议

### 5.2 装机验证清单

1. **展开首 300ms（p: 0→0.30）**：窗口从卡片生长，内容尚未淡入（alpha=0），窗口独自动画 → 应与现状一致（无内容可见，无差异）
2. **展开中段（p: 0.40→0.65）**：内容淡入，宽度贴合窗口、高度被框住（clipRect），**重点看**：内容是否读作"填满窗口"而非"被硬裁"
3. **展开完成态（p: 0.65→1.0）**：内容完全可见，宽度贴合、高度适度超出窗口被裁，**重点看**：全屏态时内容是否"填满屏幕"（无两侧色条）
4. **收起后半段（p: 0.40→0.0）**：内容已淡出，窗口独自缩小回卡片 → 应与现状一致（用户已接受的"一张纸移开"）
5. **锚行跟踪**：播放推进中开合，当前播放行是否始终对准窗口垂直中心（translationY + scale transformOrigin 的叠加效果）
6. **中断弹回**：中途松手弹回/快甩收起，scale 是否平滑回退（progress 纯函数驱动）
7. **三触发路径**：返回键/系统手势/下拉三路径收起，落点是否精确在卡片位置（窗口层公式未动，内容层 scale 不影响窗口落点）
8. **回归**：上轮已验证的 morph 架构（C3 交叉淡化、死层修复、预组合）不受影响

### 5.3 调参预案

若装机后发现"内容被框住"的边界感过于明显，可微调：

- **内容淡入窗提前**：[0.40, 0.65] → [0.35, 0.60]，让完全可见区间的超出量更小
- **clipRect 软化**（高级）：在裁剪边界附近加渐变遮罩（Modifier.drawWithContent + VerticalGradient），但这会引入额外的 draw 开销，仅在硬裁剪实在无法接受时考虑

## 六、与用户已否决方案的区别

**已否决："整窗等比缩放"**（窗口+内容作为整体等比缩放）
- 问题：末段窄高窗摊开到扁卡片，观感差（"很难看"）
- 原因：窗口与卡片宽高比相差 6.8 倍，整窗等比 → 末段非等比"摊开"拉伸

**本方案："内容等比 + 窗口非等比"**
- 窗口：保持现有非等比形变（已真机验证精确落卡），**不动**
- 内容：以窗口宽度为基准等比缩放，始终"填满"窗口宽度，高度超出被 clipRect 裁掉（读作"被窗口框住"）
- 区别：窗口轨迹完全不变（用户满意的部分保留），只改内容在窗口内的呈现方式（从"clipRect 渐进遮挡"改为"等比缩放填满窗口"）

## 七、总结

**推荐方案**：内容层加宽度基准等比缩放，clipRect 降级为保险。

**推荐理由**：
1. **数学上可行**：宽度精确贴合，高度超出被裁（不可见），视觉上读作"内容填满窗口"
2. **实现简单**：+8 行代码，graphicsLayer 纯函数，零重组/重布局
3. **性能优**：O(1) 逐帧重录，符合"提高帧率"目标
4. **架构兼容**：窗口层/触发路径/中断逻辑零影响，translationY 锚行跟踪自然叠加
5. **风险可控**：主要风险是"边界感"，可通过装机验证+微调淡入窗解决

**备选方案**：内容自适应（字号/行数插值）。仅在推荐方案实测观感仍不满意时考虑，但实现复杂度高、性能开销大、与现有架构冲突多。

**下一步**：实施 Commit 1，装机验证清单逐项过一遍，观感满意则推送，不满意则回退并记录具体现象。
