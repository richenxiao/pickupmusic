## ① 已知问题（本版本不修，留待下个版本）

### 1. 使用日志（usage_logs）未排除在云备份外，且有两处未脱敏错误串
- **现象**：`filesDir/usage_logs/usage-*.log` 会随 Auto Backup 上云；其中两条 detail 是**未经脱敏的第三方错误文本**。
- **证据**：`app/src/main/res/xml/data_extraction_rules.xml` 的 `<cloud-backup>` 里没有 `usage_logs`；`MainViewModel.kt` 里云备份失败写 `"上传失败：$err"`（WebDAV 错误串，可能含远端 URL/路径）、翻译写 `"… · ${failure.take(60)}"`（未过 `AgentDiag.sanitize`）。其余 10 处调用点是固定串/枚举/计数，**不含**对话原文、歌词内容或用户资料。
- **未复现原因**：需要真的开启 Google 云备份并触发对应失败路径才能观察。
- **验证方式**：检查设备云备份内容；或构造 WebDAV 上传失败 / 翻译失败，导出 `usage_logs` 看错误串。

### 2. `LlmClient.call` 用共享可变 `lastError` 决定"是否重试/回退"
- **现象**：翻译（`call`）与 Agent 分发（`callWithTools`）并发时，后者成功会把 `lastError` 置 null → 前者真实的网络异常不再重试，直接按"非网络失败"返回 null。
- **证据**：`app/src/main/java/com/shiyin/music/data/ai/LlmClient.kt` 的 `if (r != null || lastError?.startsWith("网络异常") != true)` 与 `if (r == null && noThinking && lastError?.startsWith("HTTP 4") == true)`；同文件 `LlmToolResult` 注释承认多处调用可能并发。
- **未复现原因**：需要两类调用恰好并发，概率低、无症状。
- **验证方式**：并发单测（一个注入失败），断言失败方仍拿到自己的错误码。

### 3. 流式路径 `resp.body!!` 无判空
- **现象**：供应商返回无正文响应（204/代理错误页）时抛 NPE——在 `try` 内，被当作"网络异常"，**不会崩**。
- **证据**：`LlmClient.kt` 两处 `InputStreamReader(resp.body!!.byteStream(), …)`。
- **验证方式**：MockWebServer 返回 204 观察是否落入"网络异常"；或直接改 `?: return null`。

### 4. Tavily `answer` / `results` 遇 JSON `null` 会让整条搜索白跑
- **现象**：`"answer": null` 或 `"results": null` 时抛异常 → 上层 catch → 该轮搜索静默变成"没有资料"。
- **证据**：`TavilyService.kt` 的 `json.get("answer")?.asString…` 与 `json.getAsJsonArray("results")`；`LlmClient.kt` 注释里已记过"JsonNull.asString 会抛 UnsupportedOperationException"。
- **验证方式**：单测构造 `{"answer":null,"results":null}` 走一遍解析。

### 5. 歌词抓取吞掉协程取消
- **现象**：取消歌词搜索（切歌/退出）时取消被当成"该源失败"，因 `http()` 是阻塞调用、循环内无挂起点，会把 LRCLIB→网易云→LrcShare 全跑完才退出。
- **证据**：`app/src/main/java/com/shiyin/music/data/lyrics/LyricsFetcher.kt:55` 的 `catch (_: Exception) { … }`（`UtaTenProvider` 已改成先 rethrow `CancellationException`）。
- **验证方式**：单测起慢源并在中途取消，断言及时返回。

### 6. `UsageLog.nameFmt` 被 IO 线程与 UI 线程共用
- **现象**：`SimpleDateFormat` 非线程安全；进程首个事件的 prune 与用户打开日志页并发时，日期解析可能错乱。
- **证据**：`UsageLog.kt` 的 `nameFmt` 同时被 `prune()`（`usage-log` 单线程）与 `files()/readAll()`（UI 线程）经 `fileDay` 使用。
- **验证方式**：并发压测；或改为方法内局部构造。

### 7. 备份恢复预览缺两个中文标签
- **现象**：备份含翻译/记忆时，预览显示英文字段名（`lyricsTranslation 42` / `agentMemory 7`）。
- **证据**：`app/src/main/java/com/shiyin/music/data/db/BackupPreviewer.kt:19-40` 的 `LABELS` 无这两项（**已核对**）。
- **验证方式**：造含这两张表的备份，打开恢复预览。

### 8. 歌单封面 `coverAlbumId` 不参与 id 重映射
- **现象**：跨设备恢复后歌单封面仍指向旧设备的 albumId → 撞号则显示别人的封面、否则空白。
- **证据**：`AppDatabase.kt` 的 `PlaylistEntity.coverAlbumId`；`BackupRemap.kt` 只改写 `mediaId`/`albumId`/`sourceMediaId`/`albumKey`/`orderedIds`/`albumKeys`，**没有 `coverAlbumId`**（**已核对**）。
- **验证方式**：两台设备各建歌单并互导备份，检查封面指向。

### 9. `BackupRemap` 对 JSON 数值只做 `asLong` —— 手工编辑过的备份会被整份拒绝
- **现象**：`"mediaId": 12` 被手工改成 `"12"` 时 `asLong` 抛异常 → 整份备份判"无法读取"，而非跳过脏行。
- **证据**：`BackupRemap.kt:110/123/139` 直接 `asLong`（**已核对**）；而 `SettingsStore.kt` 明确把"备份可被手工编辑"列为威胁模型。
- **验证方式**：把备份里某个 `mediaId` 改成字符串再导入，观察是"整份拒绝"还是"跳过并计数"。

### 10. 注释与实现不符（3 处，纯文档问题）
- `RoomMemoryStore.kt` 文件头仍写"P1 阶段不接入对话链路…谁都不 new 它"，实际已由 `MainViewModel` 实例化接线。
- `LyricsMorphOverlay.kt` 头注释称内容层"不缩放"，实现（`scaleX/scaleY = 窗口宽/内容宽`）在做等比缩放。
- `LyricsScreen.kt` 关于"关振假名"的时序注释称"假名 110ms 先消失、行高 240ms 后合拢"，实现是两段同 240ms（本轮刻意改同步）；`RubyText.kt` 类注释仍写旧的 110ms 说法。
- **验证方式**：读代码即可。

### 11. `SongStorySkill` 失败文案读共享 `LlmClient.lastError`
- **现象**：与其它 LLM 调用交错时，用户看到别的调用留下的错因或"未知错误"。
- **证据**：`app/src/main/java/com/shiyin/music/data/ai/skills/SongStorySkill.kt` 的 `val err = LlmClient.lastError ?: "未知错误"`（同文件空正文分支已改用返回值）。
- **验证方式**：歌单故事运行中并发触发一次翻译失败，看错因是否串台。

### 12. 跨设备导入时 `split_track` 会覆盖本机已有拆分（明确不修）
- **现象**：`split_track.id` 是自增主键、两台设备都从 1 起；导入别人备份时 `REPLACE` 覆盖本机同号行 → 本机拆分单曲的标题/序号被改写，其合成 mediaId 的收藏/歌单/歌词引用全部指错。
- **证据**：`AppDatabase.kt` 的 `@Insert(onConflict = OnConflictStrategy.REPLACE) suspend fun insertSplitTracks(...)`。
- **不修原因（用户裁决）**：MediaStore 的 id 跨设备无意义，按 id 判重不可行；正解（重分配本地 id 并重映射全部引用）成本高。
- **验证方式**：两台设备各建拆分并互导备份，检查是否互相污染。

### 13. `SettingsScreens` 下带输入框的子页缺键盘避让（用户指示：只记录）
- **现象**：与已修的"拆分编辑页"同一成因（AppRoot 根 Column 去掉了 `imePadding`，各页需自处理）。
- **证据**：全仓 `imePadding()` 只出现在 `AppRoot.kt`(1)、`AgentScreen.kt`(2)、`SplitEditorScreen.kt`(本版新增 1)。
- **验证方式**：进设置里带输入框的子页（自定义写真源、API Key），弹键盘看底部是否被遮。

### 15. `PlaybackService.applyAudioSettings` 的 `mono` 形参未使用，KDoc 引用了不存在的类
- **现象**：KDoc 写「**单声道**: 写 `[MonoAudioProcessor].enabled`」，但全仓没有 `MonoAudioProcessor` 这个类；`mono` 形参在函数体里从未被读。
- **证据**：`app/src/main/java/com/shiyin/music/playback/PlaybackService.kt:268`（注释）、`:278-284`（形参）、`:285-329`（函数体无 `mono`）。`grep -rn MonoAudioProcessor app/src` 只命中该注释本身。
- **未造成用户可见问题的原因**：单声道开关已两次实测下架（`SettingsScreens.kt:1447-1451`、`PlaybackService.kt:58-69` 均有记录），UI 不暴露；app 侧下发的 `monoAudio` 恒为 false（`SettingsStore.kt:185` 默认 false）。

### 16. `ListeningStats.currentWeekStartMillis` 的 KDoc 与实现相反（纯文档）
- **现象**：KDoc 写「保持与旧实现**逐字一致**…只 `set DAY_OF_WEEK=MONDAY`…**不要顺手修正**」，但函数体正是 v1.3.9 的修正版（先清到零点、再按 `DAY_OF_WEEK` 数值回退到本周一）。KDoc 的「周日会落到**前一天**那个周一」与函数内注释的「向后拨到**明天**(下周一)」也互相矛盾。
- **证据**：`app/src/main/java/com/shiyin/music/data/stats/ListeningStats.kt:31-53`（KDoc 在 `:31-37`、函数体在 `:38-53`）。
- **验证方式**：读代码；或对 `currentWeekStartMillis` 传"周日"时间戳，断言结果 ≤ now 且为当周周一。
- **注**：**实现是对的（已修），仅外层 KDoc 未同步** —— 只改注释即可。

### 17. 拆分模式下「上一首」在第一首不回退到上一个队列条目（与「下一首」不对称）
- **现象**：`next()` 在最后一个拆分曲目时会**落到下一个队列条目**（有显式分支）；`prev()` 在第一首时 `prevIdx = (index - 1).coerceAtLeast(0)` 恒等于 0 → 只把当前曲重头播，`c.seekToPrevious()` 永不执行。
- **证据**：`app/src/main/java/com/shiyin/music/playback/PlayerController.kt:814-841`（next 有回退分支）对比 `:843-867`（prev 无回退分支）；`PlaybackService.kt:206-241` 的 `handleSplitSeek` 同构（prev 分支在 `:234` 起）。
- **为何可能是有意的**：真正的"上一首"应落在**上一个条目的最后一个分段**，需要跨条目定位，成本高于收益；当前行为（重播本曲）自洽且不崩。**未判定为缺陷，记录待定。**
- **验证方式**：拆分专辑播第 1 首时点「上一首」，观察是重播本曲还是回到上一张专辑的末曲。
